# 我们对模型网关的理解

[项目介绍](README.md) · [架构详解](architecture.md) · [同类产品](comparison.md)

## 一句话定位

**FreeLLMAPI 是一个模型网关：对外提供统一模型接口，对内选择调用路线、适配不同供应商，并管理额度和失败。** 它服务于已有应用或 Agent；普通请求的主链路是“接入 → 选路 → 调用 → 返回”。

## 三方职责

| 参与者 | 输入 | 负责什么 | 输出 |
| --- | --- | --- | --- |
| 应用 / Agent | 用户目标与任务上下文 | 组织任务、提交模型请求，按需执行工具并验收结果 | 消息、上下文、工具定义与调用参数 |
| FreeLLMAPI 网关 | 客户端请求与统一令牌 | 检查能力、选取供应商 / 模型 / 密钥、转换协议、跟踪额度、处理失败 | 标准格式的回答、流式事件、工具调用或错误 |
| 实际模型服务 | 网关转发后的请求 | 推理与生成 | 回答内容、工具调用参数及用量等信息 |

这里的“统一”是接口与调用方式的统一，不是把不同模型合成一个能力完全一致的 Agent。工具调用返回后，真实工具仍由客户端执行。

## 网关内部的三层

1. **接口适配层：** 接收不同客户端协议，将参数与消息转换成可调用形式；上游响应再转换回客户端格式。
2. **路由控制层：** 检查模型能力、上下文与可用额度，根据手工优先级或动态评分选路，协调重试与冷却。
3. **状态与管理层：** 保存密钥、模型配置、额度、健康状态和统计，为后续路由提供依据。

实际选择的单位是“供应商 + 模型 + 密钥”。同一模型可以有多个供应商路线；模型名不同的回退可能改变结果质量。

## 入口与出口

应用通过 `/v1/chat/completions` 等兼容入口发送消息、上下文、模型选择和工具定义。网关对外调用供应商或自定义本地端点，再返回对应协议的结果。它还提供其他协议入口，不能将一个聊天端点等同于全部 API 能力。

统一接口减少应用端的适配工作，不会消除底层模型的上下文长度、工具能力和输出行为差异。

## 请求场景的教学推演

网页使用以下固定场景解释机制。模型 A、模型 B 均为虚构教学候选，不代表实际供应商；没有发送模型请求，阶段文字和结果不构成真实日志。

| 场景 | 路径 | 最终结果 |
| --- | --- | --- |
| 正常返回 | 接入请求 → 选择符合能力且有额度的 A → 适配调用 → 转换返回 | 客户端收到回答，网关更新用量与表现 |
| 主路线限流 | A 在尚未提交有效输出时返回 429 → 记录冷却 → 在预算内选取 B → 调用成功 | 客户端收到 B 的回答；如果跨模型，能力可能变化 |
| 全部不可用 | 检查候选后发现都无可用额度或处于冷却 | 返回明确错误；不会无限尝试 |
| 输出后中断 | A 已输出部分内容 → 上游连接中断 | 返回流式错误；不会静默拼接 B 的回答，客户端需要恢复 |

已有额度不足可在选路阶段跳过；上游实际限制与本地估计不一致时仍可能返回 429。失败切换提升可用机会，不能保证每个请求成功。

## 最重要的边界

- **调用成功与任务正确分别验收。** 网关成功收到答案，不等于代码测试通过或事实准确。
- **路由与适配分别负责。** 路由决定“调用谁”，适配处理“怎么调用”。
- **本地网关与本地推理分别看待。** 云模型请求仍会离开本机。
- **失败回退有条件。** 候选能力、额度、重试预算和流式提交状态共同决定能否继续。
- **增强能力不改变主干。** 缓存、压缩、融合与管理界面在主链路上增强体验，多模型融合另有并行草稿与综合过程。

以上理解依据[固定版本架构与源码](architecture.md)整理；真实 API 运行仍待验证。

## 如果以后自己开发模型网关

**参考所有产品来建立视野，选择一个主要架构参考，再按具体问题借鉴其他机制。** 不把所有产品的功能合并为第一版需求。

建议先将目标设为“给个人或小团队的 Agent 提供可控、可追溯的模型调用入口”。以下为我们的设计建议，不是已经完成的选型。

| 设计问题 | 重点参考 | 学习重点 |
| --- | --- | --- |
| 整体骨架 | LiteLLM | 统一接口、模型别名、供应商适配、路由与共享状态 |
| 额度与失败 | FreeLLMAPI | 额度预检、候选选择、冷却和回退预算 |
| 模型身份 | OpenRouter | 同模型换供应商与跨模型降级分别控制 |
| 规则组织 | Portkey | 条件、均衡和回退的组合 |
| 使用者管理 | New API | 用户、令牌、模型权限和配额 |
| 性能优化 | Bifrost | 结合实际负载研究性能与请求分配，区分企业能力 |
| 配置变更 | Cloudflare AI Gateway | 配置版本、发布与回滚 |

参考依据和版本范围见[同类产品对比](comparison.md)。

第一版先实现一种实际需要的客户端协议，接入两个云供应商及一个本地兼容端点，提供明确的指定模型、别名和优先级；补上能力与额度检查、有边界的回退，以及实际路线、错误、耗时和消耗记录。

验收重点是能解释“为什么选 A、为什么换 B、最后为什么成功或失败”，并明确指定模型能否替换、已输出内容如何中断、并发额度如何预留、客户端与网关的重试是否叠加、工具参数不合格如何返回。

动态评分、融合、语义缓存、充值计费和完整团队权限按实际问题逐步引入。每新增一个模块，都应对应已出现且能够验证的问题；最终以每个通过验收的任务成本和稳定性衡量收益。
